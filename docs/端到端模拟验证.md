# 本地 Docker 完整模拟

这个场景验证 Seam 的完整受控协作流程：一次提交目标和两个项目 AI，双方形成完整方案并确认同一版本，管理员批准后才在本地实施和测试，管理员查看报告、补充目标、再次审批，最后终止。

中心服务及 MySQL 使用独立 Docker Compose 项目。两个独立 Connector 以持续轮询进程留在本机，不以单轮调用或提供方优先顺序推进：消费方调用已登录的真实 Codex app-server，提供方调用确定性的虚拟 Agent。两个项目均为本次运行新建的临时 Git 仓库；不挂载、扫描或修改现存业务仓库。

## 启动中心

先构建本机协议、适配器和 Connector，再启动模拟专用容器：

```bash
pnpm simulation:up
```

默认访问 `http://127.0.0.1:13079`。修改端口时，在启动容器及运行场景时使用相同值：

```bash
SIMULATION_APP_PORT=13089 docker compose -f docker-compose.simulation.yml up -d --build --wait
SEAM_SIMULATION_URL=http://127.0.0.1:13089 node scripts/simulation/run.mjs
```

镜像、网络、数据库及数据卷属于 `seam-simulation` 项目，应用端口只监听本机。Compose 中的固定账号与密钥只用于这个隔离模拟，不能用于实际部署。容器不读取宿主机 Codex 认证。

## 运行实际场景

本机必须已有可用、已登录的 Codex。场景不会安装 CLI，也不会修改用户的登录配置。真实 AI 调用会使用当前账号的模型额度。

```bash
pnpm test:simulation
```

若 Codex 不在 PATH，通过适配器已有的 `SEAM_CODEX_COMMAND` 配置其可执行路径。app-server 的会话状态保存在本次临时目录的 `codex-state` 中，不写入合成项目的实现目录。

运行器创建模拟管理员、两个项目及 Agent，再走简洁创建 API 自动加入双方并开始规划。默认模拟管理员为 `simulation-owner@seam.test`，密码 `LocalSimulation!2026`；如设置 `SEAM_SIMULATION_EMAIL`、`SEAM_SIMULATION_PASSWORD`，重跑时仍需使用相同值。所有 Agent Token 仅在运行器内存中使用，不打印或存入证据。

## 验证内容

1. 提交修订1目标，双方分别提交本方分析，由协调方形成唯一完整契约。虚拟端直接核对结构化serviceExpectations中的就绪状态和当前修订，缺漏时提出具体异议，修订后双方确认同一 `revision/documentHash`；不要求在接口描述重复相同文字。初稿完整时直接确认，不为测试强迫模型生成缺陷。
2. 管理员批准前，对两个项目的文件内容做 SHA-256 快照比对，确认没有新增或修改实现文件。提前批准、提前执行测试被拒绝。
3. 初始项目没有实现、服务进程或联合脚本。批准后，虚拟提供方实际创建 `service.mjs`、`server.mjs` 和 Node 测试；真实 Codex 独立创建 `client.mjs`、单元测试与 `joint.test.mjs`。双方运行真实命令并提交 `execution.report`。
4. 提供方服务延迟启动，通过 Connector 实际健康探测后用 `service.publish` 共享动态地址。消费方按已批准用例真实调用 `POST /quote`；平台内建 `joint_verifying` 保存关联实际断言、命令和退出码的报告。运行器随后用独立 HTTP 复核补充验收证据，不作为两端预先存在的服务。
5. 管理员补充折扣目标形成修订2；旧版本、旧 hash 不能再次授权。重新规划、双方确认、批准后修改代码和测试，联合验证折扣0、10、100及错误输入。
6. 默认继续修订3把数量上限由100替换为50；修订4撤销该限制恢复100；修订5撤销折扣扩展并要求出现该字段返回400。未来要求只在追加时引入，不预写初始README。每轮重新确认和批准，全部批准用例须覆盖完整requiredAssertions。修订3后重启本次空闲Connector并模拟交接检查点丢失，保留同一thread并重新同步；实际模型压缩事件另由受控适配器测试覆盖。
7. 只读用户和 Agent Token 不能执行管理员批准或终止动作。
8. 管理员终止协作后，任务停止，不可继续派发或批准；旧完成回执不能重新生效，两个项目文件保持不变。

场景通过标准是所有断言通过，最终日志出现 `simulation-completed` 且 `ok=true`。中心健康、Agent 在线、CLI 成功退出均不单独作为通过依据。

## 真实中断与恢复

```bash
pnpm test:simulation:recovery
```

独立 Git 项目中的真实 Codex 前台执行 90 秒长命令，写出启动标记后由测试管理员暂停。运行器丢弃一次已落库停止确认的响应，检查本机待发停止回执跨 Connector 重启后补发。超过原期限确认完成标记不存在，再恢复同一批准版本，真实 Codex 执行预先批准的剩余步骤，断言长命令启动计数仍为 1。协商和批准回执为明确标注的合成夹具；真实执行、中断和恢复由本机 Codex 完成。它与主流程的真实协商、多轮实施及联合验证分别计证。

## 输出和诊断

启动日志显示本次目录，例如 `/private/var/folders/.../seam-full-simulation-...`。目录中保留：

- `provider/`、`consumer/`：双方实际实现及测试。
- `revision-N-approved-plan.md`：批准的完整共同方案。
- `revision-N-report.json`：双方执行回执和真实 HTTP 联合检查结果。
- `revision-N-joint-publication.json`：实际联合检查写回 Seam 的产物标识及文档哈希。
- `result.json`：最终通过报告；失败时为 `failure.json`。
- `run-index.json`：本次批次、状态与原生会话链接；`codex-state/telemetry/`：本机采集的逐轮观察指标。
- `codex-state/`：本次专用 app-server 会话状态，按私人本机资料保留。

失败会返回非零退出码并保留已取得的证据，不以 Mock 结果代替真实 Codex 成功。可查看模拟中心日志：

```bash
docker compose -f docker-compose.simulation.yml logs --tail 100 app
docker compose -f docker-compose.simulation.yml ps
```

停止容器使用 `docker compose -f docker-compose.simulation.yml down`，保留模拟数据库以便复核。只有明确不再需要模拟历史时，才删除其专用数据卷。运行器不会清理其他容器、卷、浏览器或现存项目。

本场景只证明 Seam 对合成报价项目的协商、审批、两端实施、测试、修订与终止链路。实际协同平台、智能体平台的业务实现、凭据和生产部署仍需各自真实验收。

双方 AI 的本方实施报告先提交，随后平台内建联合验证；独立运行器的 HTTP 复核在这些报告收齐后执行。运行器实际检查通过后，会另发布“第N轮 HTTP 联合验证”测试报告产物，包含实际请求数、修订、批准文档哈希及本地报告文件的 SHA-256；不会改写 AI 原始回执或声称已部署。平台中的联合验证产物与两端实施报告应一起阅读。

对已经在运行、尚未包含自动写回逻辑的旧模拟进程，可从真实结果文件补发证据：

```bash
node scripts/simulation/publish-joint-evidence.mjs \
  --run-root /path/to/seam-full-simulation-RUN \
  --collaboration-id COLLABORATION_UUID --revision 1
```

增加 `--wait-ms 900000` 可在本次任务中等待指定修订的实际结果文件产生后上传。没有真实 `joint.status=passed`、HTTP 请求数、匹配的批准文档及平台修订记录，脚本会拒绝上传通过结论。上传仅包含明确字段，不发送源码、绝对路径、凭据或完整模型日志；相同结果重复补发不会创建新产物或新版本。

## 浏览器界面验收

针对同一 Docker 模拟中心，另运行浏览器测试：

```bash
SEAM_E2E_EMAIL=simulation-owner@seam.test \
SEAM_E2E_PASSWORD='LocalSimulation!2026' \

```

显式设置 `SEAM_E2E_BASE_URL` 后，Playwright 只复用该服务，不会另外构建或启动端口3000的应用。浏览器使用独立临时配置，不复用日常 Chrome 资料。在本机 Codex 中启动测试时，须遵守当前 `AGENTS.md` 的 Chrome 规则，通过正式流程申请沙箱外执行，保留 Chromium 自身沙箱。

四项界面测试分别验证：

- 登录、实际创建项目和 Agent，只提交目标和两端项目即可自动加入双方、派发只读规划任务。
- 管理员在真实页面审阅两轮完整文档、分别批准、查看双方报告、补充要求并手动终止；同时验证只读用户没有管理按钮、越权请求403、旧版本批准409，终止后保留文档报告并隐藏继续执行入口。

## 轮询断连和交付恢复

```bash
pnpm test:simulation:poll-recovery
```

此专项通过实际 Next.js HTTP 服务验证领取协议，不调用模型。先建立一个旧版20秒空闲长轮询，断开连接后再创建任务；新连接必须在第一次领取取得该任务，旧连接不能抢走它。再故意省略一次交付确认，等待60秒交付租约到期，检查同一任务由新attempt重领，旧attempt心跳要求停止且完成回执返回409，当前attempt确认后才取得20分钟执行租约。

Connector正常轮询改为立即返回，无任务时遵守本机pollMs间隔。服务端兼容旧长轮询，但监听请求断开；领取后发现断开，仅按任务ID/attempt释放自己的领取。即使响应在最后一次断开检查后丢失，也只有60秒交付租约；Connector须先用当前attempt心跳取得执行确认，才记录开始并运行本机Agent。执行期间原有心跳继续续租。五轮脚本还实际重启空闲Connector验证下一轮可继续；失败时自动暂停本次协作并保存现场。

六项优化的实际五轮结果、重启故障修复、真实恢复及完整证据口径见[2026年11月13日六项优化验收记录](验收测试记录-2026-11-13-六项优化.md)。此前日期的两轮和八项优化结果保持历史记录，不用新数字覆盖。

## 人工批准修复与自动资料获取专项

```bash
SEAM_SIMULATION_URL=http://127.0.0.1:13089 pnpm test:simulation:repair-information
SEAM_LIFECYCLE_TEST_URL=http://127.0.0.1:13089 pnpm test:lifecycle
```

使用已启动的隔离中心；生命周期HTTP专项的地址变量是 `SEAM_LIFECYCLE_TEST_URL`。该场景只做两版：真实Codex先从虚拟对端项目询证公开协议标记，首版批准后注入实际HTTP金额错误，联合验收失败使平台自动起草修复版。修复待批准期间比对双方文件哈希、核验旧批准及提前测试拒绝、直接复查原错误仍在；测试管理员批准新完整文档后，再实施、联合验证并手动终止。业务范围保持基础报价，不新增折扣等后续五轮目标。

额外输出 `information-evidence.json` 和 `repair-approval-evidence.json`，第1版报告如实为失败，第2版须实际通过。两端仍是一个真实Codex和一个确定性虚拟Agent；真实浏览器用合成回执另外验证人工点击修复批准。机制及升级说明见[修复审批与自动资料获取](修复审批与自动资料获取.md)。
