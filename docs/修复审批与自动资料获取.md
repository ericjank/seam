# 人工批准修复与缺失信息自动获取

平台维护协作状态、消息路由、资料来源和审批记录；项目分析、方案设计、编码和测试由各端本地 Agent 完成。中心没有新增模型服务，也不扫描各端源码。

## 失败后的流程

1. 收齐本方实施失败报告，或完整联合报告含 `failed` / `not_run` 时，原修订报告保留原状。平台创建下一修订，记录失败项目、用例、原文档和原报告哈希。
2. 两端在只读权限下分析失败证据，提交本方修复计划；协调方汇总完整修复契约，双方确认相同文档哈希。
3. 新修订的批准为空。管理员审阅页面上的失败报告和修复文档，点击“确认修复方案并重新实施”。旧批准、Agent确认、原先通过的用例都不能替代本次批准。
4. 批准后才重新实施和验证；再次失败仍进入同样的人工门控。成功后等待管理员审阅并手动终止。

修复保留原有效要求ID、验收用例ID及执行方、必需断言和服务就绪检查，可以增加覆盖。文字说明和具体修复步骤由双方及管理员审阅；平台的结构校验不能证明所有业务语义等价。需求变化仍由管理员追加要求。管理员可在修复草案未批准时终止，报告明确记录“没有重新实施或验证”，不会显示修复通过。

`not_run` 与明确等待同时返回时，继续等待，不提前完成联合阶段。已经实际执行的失败证据优先保留，不能被通用“需要人工”标记吞掉。

## 自动寻找缺失事实

Agent 可在已有本地及共享检索后提交 `information.request`，问题与两类检索来源必须完整。旧式缺失事实阻塞则先分配本端 `local` 查找任务，再转对端 `peer` 任务。即使对端已提交本阶段计划或报告，仍可领取这个询证任务。

各端用 `information.respond` 回答 `found` 或 `unavailable`，附原文答复和来源。多方协作收齐指定对端的答复后再续接，保留冲突原文供本端核对，不由平台猜测真值。成功后清除对应阻塞并自动继续原阶段；原有效批准和业务目标不变。冲突事实涉及改变已批准契约时，不能直接改目标。

查找任务的本机约束：

- 原生 Codex 强制 `read-only`，关闭网络；即使当前主阶段已经批准实施也一样。
- 不领取凭据，不运行 Connector 配置的测试，不检查或更新实施基线，不启动服务。通用适配器的操作权限仍由本机运行工具约束。
- Connector 仅为本地 Agent 建立文件索引：最多100项、目录深度2、跳过隐藏项、依赖、构建输出、常见密钥文件和符号链接；最多列20条 package.json 测试相关脚本文本，查询时不执行。
- 文件内容留在本机，仅明确提交的答复和来源返回平台。来源使用相对项目路径，拒绝明显绝对路径、上级路径和常见秘密文件引用；这不是任意内容的自动保密证明，各端仍需遵循本地发布范围。

每项目每修订最多3项信息请求，相同待处理问题去重。穷尽本地、共享和指定对端后，页面才显示补事实入口；管理员补充后留存提供时间并续接。真实权限不足通过 `workflow.blocked.requiresAuthorization=true` 直接阻塞；补事实不改变本机权限策略。临时错误第三次及循环等待也先做有界只读诊断，不无限唤起模型。

## 升级与兼容

数据库迁移 `0005_even_lady_vermin.sql` 仅给修订表添加 `repair_context` 和 `information_requests` 两个可空JSON列。先完成正常备份，再按现有部署方式迁移和构建；不要删除历史失败报告。

服务端与双方 Connector 一起升级并重启。新版轮询声明 `supportsInformationLookup=true`；旧版默认不支持，服务端不向它交付查找任务，包括领取时才刷新成查找任务的情况。旧客户端不会被假定具有新权限或自动升级能力。交接版本5继续使用增量资源引用，只在首次及必要恢复时重同步，不在每轮对话粘贴全量JSON协议。

## 专项复现

```bash
pnpm build
SIMULATION_APP_PORT=13089 docker compose -p seam-repair-information -f docker-compose.simulation.yml up -d --build --wait
SEAM_SIMULATION_URL=http://127.0.0.1:13089 pnpm test:simulation:repair-information
SEAM_LIFECYCLE_TEST_URL=http://127.0.0.1:13089 pnpm test:lifecycle
```

专项使用真实本机 Codex 消费方和确定性的虚拟提供方。公开协议标记只保存在提供方项目；消费方自动询证取得。提供方首次HTTP层故意注入真实金额错误，联测必须检出；随后验证自动起草修复、批准前代码哈希不变、批准后真实修复与HTTP复验。测试管理员由运行器调用公开API；另用真实浏览器点击修复批准按钮验证界面流程。不将虚拟端、合成协议回执或故障注入表述为两个真实模型或生产业务验收。
