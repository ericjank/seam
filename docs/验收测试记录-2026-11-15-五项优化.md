## 改动与证据

1. 协议 6 能力预检、旧端队列兼容、10 分钟资料期限、三个 attempt 的有界恢复及人工重新查找。真实 MySQL 验证查询在队首时旧客户端仍可领取后续普通任务，迟到回执被拒绝。
2. 按问题独立预算，共享事实索引跨修订保存来源版本、SHA-256 和 TTL；缓存先由资料拥有端只读核对，变化重新查找。三方真实 HTTP 回执矛盾时先协商，一致后才归档；四个成功问题不耗尽其他问题预算。
3. 区分代码、环境、权限、缺失事实、未知原因。非代码失败保留原修订，管理员确认后才重新实施/验证；先前失败进入归档。实际浏览器点击确认重试、核对只重跑受影响方、保留第 1 修订及失败历史，最后手动终止。
4. 测试指纹进入完整计划；实施后冻结集合，联合阶段新增、修改、删除测试均停止。现有测试变更必须逐文件声明原因并重新批准。固定 Connector 独立 HTTP 检查绑定批准规范及文档，实际金额错误不能被同名测试“通过”掩盖。完整 Connector 哨兵测试验证指纹异常后既不调用模型，也不运行本机测试。
5. 修复使用 `plan.amend` / `plan.patch`；完整新版仍需双方和管理员确认。配置命令、真实断言、独立检查完整时直接汇总联合回执。端点/修订使用环境绑定，修复不再为修订号改测试。资源命令归因修复相对路径及 Mac 别名，旧公开操作回放从 3 次校正为 8 次。

公开 `contractVersion` 最初只在提供方文档中，真实 Codex 自动询证取得，不由管理员填写。第一轮 HTTP 层预设额外加 1，真实小计为 24001，双方独立检查均失败。原报告保留，新版清除旧批准，先只读起草修复。修复批准前文件快照不变且 HTTP 故障仍存在。管理员确认完整第 2 版后修复，双方各 10 条真实联合测试通过，独立 HTTP 检查通过；两侧测试文件哈希与第 1 版相同。

消费方实施时 `node --test` 的 3 个单元用例通过、10 个无服务环境变量的联合用例跳过；跳过不计联合通过。两轮真实联合回执共 4 份由 Connector 直接汇总，原生会话没有 `integration.report` 模型轮次。平台保存两次批准和一次手动终止，原失败报告与修复来源哈希一致。

首次预检为修正差异字段默认值主动中止。正式流程中自动回执使联合阶段短于旧运行器轮询间隔，运行器未采到其瞬时状态；原始结果已持久化且 Agent 已开始修复。已改为依据持久化修复里程碑判断，本次恢复控制器接续同一任务及持续轮询的 Connector，无新会话、无项目重建或凭据读取。旧控制器内存 stdout 未另行导出；全部任务结果、实际命令输出和公开原生操作完整保留。

正式流程启动后补上的路径别名统计与暂停状态防护，以单独回归和真实公开操作回放验证，不回写历史遥测。两个不同模型运行的耗时、输入/缓存计数不视为固定性能提升或精确账单。
